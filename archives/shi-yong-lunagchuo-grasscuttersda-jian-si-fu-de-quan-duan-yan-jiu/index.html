使用LunaGC或Grasscutters搭建私服的全端研究

本文主要介绍在各个平台游玩原神私服, 目前linux, windows, 安卓, iPhone都可以运行, 本文还处于更新当中肯定有很多问题

本文使用的原神版本为7.0, 低版本或高版本可能不适用

https://shop.mhdy.net

1. 服务端

服务端使用普通的https://github.com/Merprose2/LunaGC-Renewed 目前服务端的资源有一定的缺失, 不确定后续会不会补全

1. 请求流程和相关问题

原神客户端接入 LunaGC 时，需要依次完成启动初始化、账号登录、区服查询、资源初始化和游戏网关连接(PC还需要请求安全文件)。本项目先后处理了移动端资源页面显示 0 GB、iOS 收到错误平台资源信息，以及 PC 7.0 启动安全文件返回空正文的问题。后者通过独立插件提供已验证的原包，再由客户端启动代理回放.

flowchart TD PCInit[PC 启动早期安全文件请求] --> Replay[独立插件提供原包，客户端代理回放] Replay --> Client Client[Android / iOS / PC 客户端] --> SDK[SDK 账号登录与 Combo] Client --> Dispatch[HTTP Dispatch 服务 · 22100] SDK --> HTTP[LunaGC HTTP 认证接口] Dispatch --> QRL[query_region_list] Dispatch --> QCR[query_cur_region/os_usa] QCR --> Plugin[按平台合并资源 metadata] Plugin --> Crypto[响应加密与签名] Crypto --> Client Client --> CDN[官方资源 CDN] Client --> Gate[游戏网关 · UDP 22101] HTTP --> Mongo[MongoDB] Gate --> Mongo

/status/server 返回版本，只说明 HTTP 服务可达。SDK 返回登录成功后，客户端还要接受 Dispatch 响应、初始化资源，再与 UDP 网关握手。

PC额外需要请求安全文件, 官方的安全文件会随着版本更新而移除低版本的响应所以服务端需要自己处理. 并且请求早于SDK/Dispatch 私服重定向, 所以没有处理的话会登录失败.

2. 资源包处理

安卓/ios需要请求服务端以下载资源, lunagc默认没有返回官方的资源地址所以请求时会空回导致客户端显示资源大小为0GB

这里通过设计了一个 AndroidDispatchResources 插件来解决这一问题，在 QueryCurrentRegionEvent 中取得尚未加密签名的 protobuf 响应，合并官方资源字段，再交回服务端原有处理链。

模板限制为 256 KiB，主资源 URL 必须是有效 HTTPS 地址。模板里的额外字段和 protobuf unknown fields 会被拒绝；原响应中的 gate、密钥和 unknown fields 则通过 builder 保留。正数 client_data_version 需要配套的 data_url，未提供的基版 data/silence 字段沿用原响应。

这一区分很实用：资源插件只需要补齐已知缺失的数据，不必复制一份完整 Dispatch 响应并承担所有字段的维护。

3. 登录时欢迎等字段异常

SDK 的一个中文语言 URL 落入 LunaGC catchall，HTTP 返回 200，但内容为空，界面显示 tips_enter_game 字面量。通过 Nginx 精确 location 提供客户端自带的 548 项中文语言表后，欢迎文案恢复.

不经过Nginx代理这里可能无法处理, 小问题不影响流程进行未对lunagc做修改

5. PC安全文件

测试时刚好经历了原神从7.1更新到7.2, 然后PC无法登录LunaGC因此发现了PC需要请求得到安全文件后才能继续执行登录等流程.

官方只保留了当前版本和上一版本的完全文件所以7.1时期可以登录而到了7.2无法登录.

PC 在进入 SDK 登录之前会访问官方 /query_security_file?file_key=OSRELWin7.0.0 LunaGC对这一路径的响应默认为空.

实测发现对7.0返回7.1的安全文件也能通过验证所以通过新增 SecurityFileReplay 插件，用现有 Javalin 注册 GET。插件数据目录存放官方 OS 7.1 原始响应，启动时核对长度和 SHA256；仅当 file_key=OSRELWin7.0.0 时返回 24,424 字节原文，其余请求保持空正文。

回复不包装 JSON，也不使用离线分析产生的 decoded 二进制。

2. 客户端

1. 安卓

安卓端的修改是基于https://github.com/Xuoos/AnimeGamesProxy

项目做的修改, 主要修改为内嵌进apkm安装包, 增加gm工具, 增加帧率解锁, 增加mod管理器

1. APKM 的分包结构

修改源是通过第三方下载的官方国际版7.0.0 APKM

APKM 外层有六个成员：

TEXT6 行展开代码收起代码

base.apk 承载应用入口、SDK 和 NPatch 模块；split_AssetBundles.apk 承载内置资源；arm64 split 保存原生库。后续每个版本都围绕一个确定的修改点构建，例如 v9 改资源 split，v10 只换 base 里的 runtimefix 模块。

NPatch 内嵌两个模块：AGP 4.6 和本项目自己的 org.lunagc.runtimefix。AGP 负责私服转发与游戏 RSA；runtimefix 补充 SDK URL、账号公钥、私服 CA，并逐步加入 GM、帧率和分辨率功能。

本项目已对代理, 帧率解锁, mod管理器进行了合并并重新设计了界面, 安卓和ios默认资源贴图像素较低分辨率解锁没有实际意义暂时先放弃并移除了.

三份安装 APK 必须使用同一证书。NPatch 默认签名输出、官方 split 和工作包不能随意混装。外层 APKM metadata 保留原始字节，安装器没有要求的 hash/size 字段不自行添加。

2. SDK 账号 RSA 与服务端不匹配

安卓默认的RSA公钥是2048位, 而服务端认证使用的对应密钥不同会导致4214报错, 通过插件来进行RSA修补/替换解决.

单独替换过于麻烦后续把 SDK 修复迁入独立模块，同时恢复完整官方 origin。账号 hook 精确接入RSAUtils.encryptByPublicKey(byte[], byte[])

第二个参数只有在 DER SHA-256 命中官方固定公钥时才替换。这里有一个容易写错的角色关系：Android 模块内的替换公钥匹配的是服务端 auth fallback，不是 SDK private_key.der。(这里属于历史包袱, 通过修改应该是可以直接匹配SDK默认私钥)

四者需要分别核对。用某一把公钥或证书“全部替换”，会混淆本来独立的流程。

私服 TLS 支持采用 CompositeTrustManager：先调用系统验证，仅在 CertificateException 后尝试固定 CA 的独立 store，保留 hostname 传递。SDK URL 修复也限定到 area=os / env=2 的 25 个固定字段，并要求当前值仍与官方原值一致。只在通过域名并开启HTTPS时需要, HTTP ip+端口不需要, 并且本项目没有对这里做处理.

4. SDK 在代理之后又改了一次 host

通过使用http代理服务端到lunagc后登录报错http_unknow_host 而通过外置代理或dns或host修改指向时可以正确登录.

实际定位到 ServerRegionInterceptor.replaceHostInUrl：AGP 先把请求改到私服 IP，SDK 随后又把 host 改回 dispatchosglobal.yuanshen.com，但 scheme 和端口仍保留。

后续在 after hook 中采用很窄的恢复条件。下面是逻辑示意，privateHost 对应本项目构建时固定的私服 IP：

Java7 行展开代码收起代码

最后一个条件证明 SDK 只改了 host，返回完整原 HttpUrl 就能保留 scheme、port、path、query、userinfo 和 fragment。其它 URL 变化和原异常继续沿用原行为。

两次真机日志都实际命中 shapeMatch=true / preserved=true，before/after scheme 为 HTTP、端口均为 22100。关闭外置代理可以正确进入游戏了.

这次成功把一个模糊的错误文案收窄成了具体的 URL 改写顺序。ErrorTranslator 的 http_unknow_host 是泛化默认错误，单看它无法确定错误来源。

只替换 base 内的 assets/npatch/modules/org.lunagc.runtimefix.apk，其余 1,028 个非签名条目和两个 split 保持不变。NPatch 用模块 ZIP CRC 派生缓存路径，因此保留数据、同 versionCode 的更新也能刷新模块，不需要清理游戏资源。

v13 增加 SurfaceHolder 尺寸拦截。当前源码还包含对 ScreenManager::SetResolution 两处指令的运行时修改尝试，偏移为 0x8966950 / 0x8966974，需要通过 mprotect 改页权限。

v14 的记录改为离线修改 arm64 原生库，把两处分辨率初始参数、两处 SetResolution 参数、getter 两条指令、setter 和帧率变量固定为目标尺寸及 120。这是作用于游戏软件的 ARM64 指令与数据补丁。

帧率解锁实测有效, 但画质解锁后看起来并没有变化, 对比PC资源发现安卓贴图资源只有1024x1024而PC有2048x2048, 修改分辨率没有价值所以后续放弃了.

2. PC

此处的PC更多指的是Linux, Windows默认兼容足够, 几乎不需要修改什么.

mod加载器使用xxmi而非原生3dmigoto, Linux兼容层使用DWProton

1. 安全文件请求

前一天使用TwinTailLauncher通过了所有测试, 而第二天想要脱离TwinTailLauncher时发生了错误, 现象为启动后静默退出, 错误只有initDriver Failed: Error [4,643,0]

转折来自一条启动早期请求：客户端向官方查询 7.0 安全文件，收到 HTTP 200，却没有正文。保持同一客户端、DWProton 16 和独立前缀，只将这个空回复替换为通过 7.0 公钥外层校验的官方 7.1 原包后，游戏进入登录流程并成功加载世界。随后用日常 GIMI 入口重测，也没有问题.

本文记录这条证据链、之前没有解决故障的维护尝试，以及最终可用的运行流程。结论适用于本项目的国际服 Windows 7.0 客户端和 LunaGC 环境；没有找回原始 7.0 安全文件，也没有确定官方回复变空的日期。\推测为官方更新导致, 因为可以返回的是7.1和7.2, 其他版本均无返回.

2. 修改补丁以兼容Linux

lunagc提供的Astrolabe.dll补丁默认只兼容Windows, Linux使用时出现错误, 后续通过修改解决. 不确定通过其他方法是否可以不修改, 本文使用修改过的为例子.

DLL 仅文件偏移 14975 处一字节不同（.text 段，RVA 0x467f）：

- 上游：48 85 C0 74 20 → test rax,rax; je +0x20（条件跳转）

- 修改版：48 85 C0 EB 20 → test rax,rax; jmp +0x20（无条件跳转）

3. 使用脚本代替

脚本启动临时回放代理，再调用 start-gimi.sh，由 DWProton 16 启动 XXMI loader 和游戏。Steam 客户端无需启动，Proton 仍读取本机 Steam 的部分兼容文件。对steam有一定的依赖, 可以通过修改解除依赖.

三份 Mach-O 的代码签名区还包含 Apple 签名链相关 RSA 公钥，它们属于代码签名，不是游戏协议密钥。

早期曾把部分 SDK 槽当成游戏签名槽，进而误以为静态公钥都已经对齐。后来的 native 调查发现，游戏 QCR 和 Token 路径把公钥用 ARM64 指令逐段构造出来，根本不依赖这几处明文 PEM。

因此，扫描到哪些公钥和运行时究竟调用哪套 RSA，需要分别回答。

F 系列尝试过 SDK 静态改写、网络转发、Security.framework hook 和 native memcpy 观察。它积累了几类值得保留的失败经验。

单库替换后没有重新签名

一次独立 dylib 替换被 dyld 以 code signature invalid 拒载。CodeDirectory 页摘要正确，仍不足以满足实际安装环境的签名要求。后来按用户原有 LiveContainer 流程替换旧库并强制签名，F5 才确认执行。

追加一个新注入项也不会自动删除旧库。更新需要明确旧库的加载来源，否则多个版本可能同时存在。

LiveContainer 中的 image 0 不一定是游戏

早期 native caller 范围判断直接把 _dyld_get_image_header(0) 当作游戏基址。一次采样所有候选都被 range 条件挡掉，后来启用 LiveContainer 的隐藏容器选项后，range 拒绝计数降为 0。

但替换计数仍然为 0，格式识别未命中，4214 继续出现。修正基址识别解决了一个诊断障碍，并没有自动解决 RSA 路径问题。

主程序不是可直接 dlopen 的动态库

旧 FILES1 交付原始 MH_EXECUTE 主程序，用户替换并强签后仍报 cannot dlopen a main executable。后续 LC2 根据 LiveContainer 的固定版本实现转换为 MH_DYLIB，调整 header flags、__PAGEZERO 并加入 LC_ID_DYLIB。

LC2 至少部分启动到了 F7 面板/登录界面，但仍有间歇性 SIGTRAP。缺少完整镜像表和调用栈时，单独一个运行地址无法确定具体故障函数。这条路线的稳定性问题没有取得最终修复结果。

四、关键事实与边界

  • R1 失败根因：只换密钥不换块长（Swift 包装按 256 字节分配、实际写 128 字节、发整个数组 → 服务器拒绝；Base64 344、尾 128 字节零）。

  • 日志显示 LunaRSA R3 是预期（dylib 未变），R4/R5 变化在主程序，以 IPA 文件名/Storage ID 区分。

  • 未验证：资源下载完成、进入游戏世界、服务端日志重核；R6/R7 已交付但无真机结果。

  • 私服地址为 dispatch-target.json 原样记录（该域名隐藏真实 IP 信息）。

1. R1 到 R2：只替换公钥，为什么输出仍然错误

RSA-only R1 使用 fishhook 接管 Security.framework 的导入符号，按公钥摘要把 SDK/auth key 映射到当前服务器。它能命中映射，却仍在 SDK 账号解密阶段失败。

设备日志显示一个很有辨识度的结构：

TEXT3 行展开代码收起代码

主程序的 Swift 包装代码先调用 SecKeyGetBlockSize(originalKey)，按官方 2048 位 key 分配 256-byte 数组。R1 只在 SecKeyEncrypt 时换成 1024 位 key，实际写入 128 bytes，而包装代码仍追加整个数组。

TEXT6 行展开代码收起代码

服务端将整段密文交给 1024 位私钥解密，拒绝了这段过长的输入。这个错误发生在账号字段，尚未进入密码校验和 QCR。

R2 为 SecKeyGetBlockSize 增加与加密相同的 key 映射，使数组分配、分块和实际输出都使用 128-byte 块长。补丁内部识别原 key 时调用保存的原始函数，避免递归。

针对性回归复现了旧版的 128-byte 零尾，并确认修复后输出为 128 bytes、Base64 长度 172；用户随后确认 R2 的 SDK 登录成功。

这次问题的关键在调用方合约：更换一个密码学对象，会同时改变块长、分块上限和缓冲区分配。只拦截最后一次加密调用，可能漏掉前面的尺寸查询。

R3 采用与 Android 类似的完整 HTTP Dispatch 转发，在：

这里还有一个 Objective-C ABI 细节：方法属于 new 家族，返回对象的所有权是 retained。函数指针和替换函数都需要保留 NS_RETURNS_RETAINED，不能按普通 autoreleased 返回值包装。

5. R6：把游戏公钥修改移入运行时函数表

静态定位进一步发现，七处签名公钥构造最终都使用同一个 RSA 类的参数导入入口：运行时函数表第 18 槽，ARM64 下偏移为 18×8=0x90。部分调用经过中转函数，所以不能只搜索直接的 ldr ..., #144。

参数 ABI 是一个 64-byte 结构，包含八个 managed byte-array 指针：

TEXT8 行展开代码收起代码

R6 在首次转发 Dispatch 请求创建前安装 hook。实现先核对完整主程序 UUID、相关函数前缀指令、类初始化状态、函数表页权限和原槽位目标；必要时调用游戏自己的加锁初始化入口，再原子替换函数指针。

替换条件同时要求：

  • 指数为 01 00 01，即 65537。

  • 模数长度为 256 bytes，全部字节精确匹配已定位官方公钥。

  • 六个私钥参数均为空。

命中时改写本次新建数组的模数，再调用原导入函数。加密、填充和验签继续由游戏执行。这条路线覆盖七处相同公钥的导入，不再依赖逐处修改主程序立即数。

验证基线也随之改变：R6 使用原公钥主程序。若继续用已经静态修好的 R5 主程序测试，即使新 hook 没生效，也可能误判成功。
